# Feed-Forward

Read at Step 8. Propose-only: log, count, propose. Nothing writes the brain or another skill.

## Mechanism

1. Each weekly and since run appends `_patterns.md`: date, deal slug, segment, stage, flags. No names, amounts or quotes. Each run also updates `_gaps.md`: the missing-field questions asked, and how many were filled by the next run.
2. A pattern is proposed only at the n below, counted as distinct deals inside 180 days. Below n it stays a note.
3. A proposal is exact text plus the receiving skill. The approver says yes, then runs the receiving skill. Unattended runs log and propose nothing. Never in a seller's thread.
4. No seller is ever a unit: counts are by deal, segment, stage and field.

| A CRM field missing in the same way for 3 weeks | 3 weeks | The CRM owner named by the approver, as a note |
| A question asked in a DM that the next run found filled | 5 | The approver, as proof the ask works |
| A hypothesis worth testing on about ten deals | 1 | `experiment-doc` |
| Ledger rows | n/a | `meta-synthesis` via `/context/learning-sources.md` |

## Reads (read-only, each named on a "Learned from" line with skill and date)

Brain Sections 2, 3 and 8; `deal-review` `_patterns.md`, `_outcomes.md` and `_gaps.md` for the segment (never `_mine.md`); `prospect-research` `_outcomes.md`; `discovery-call-scoring` `_reviews.md` counts only; `customer-context` `_patterns.md` for renewals. Learned items shape questions and the order of checks; they never become proof of ours. A conflict with a confirmed brain value is shown as a question with both values.

## Rules

- A seller-reported outcome is labelled seller-reported.
- A rate shows only at 10 or more deals; below that, counts.
- A proposal that conflicts with a confirmed brain value is a question, not a replacement.
- `sales-research-digest` reads `_patterns.md`, `_gaps.md` and `_outcomes.md` here as counts, never a seller.
